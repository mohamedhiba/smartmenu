1 · The problem

You are in Rome. The menu is in Italian. You are keto.

Google Translate gives you words. It tells you that trofie al pesto is “trofie with pesto”. It does not tell you that it is 76 grams of carbohydrate, or that pesto contains pine nuts even though the menu never says so.

Anyone eating to a rule — keto, coeliac, vegan, a nut allergy — is doing two translations at once. The language, and then the ingredients. The second one is the one that actually matters, and it is the one no tool does.

What SmartMenu does instead

  1. You photograph the menu.
  2. You tap your diet and any restrictions. Three taps.
  3. Every dish comes back translated, with estimated macros, allergen flags, a score out of 100, and a plain-English reason for that score.
The sentence to land on: the ranking is not a translation, it is a decision. We do not tell you what the dish is called. We tell you whether to order it, and why.

Real output, from a real photo

2 · The one decision worth defending

If a judge only remembers one technical thing, make it this. Everything else is execution.

The obvious build

photo → Google Vision OCR → GPT structuring → Google Translate
      → FoodData Central lookup → scoring → UI

Five APIs, five sets of credentials, five failure points — and a nutrition lookup that has to fuzzy-match “Trofie al Pesto Genovese” against a database keyed on “pasta, cooked”. That last step alone is a research project.

What we built

photo → downscale in browser → ONE multimodal call (strict JSON schema)
      → validate → score → ranked menu

Why this is the right architecture, not a shortcut

  • A vision model reading a menu does not need OCR as a separate step. It reads the image directly. Handing it pre-extracted text would actually lose information — layout is what tells you which line is a section header and which is a dish.
  • Translation is free once the model is already reading. Asking for output in the target language costs nothing extra.
  • Ingredient inference is something only a language model can do. No database knows carbonara contains egg and pork when the menu just says “Spaghetti alla Carbonara”.
  • Nutrition estimation is honest about what it is. A restaurant does not publish macros. A lookup on a fuzzy foreign dish name would be an estimate too — just slower, wearing a lab coat.
The half that is deliberately not AI. Scoring is a pure function in lib/scoring.ts. The same dish and the same preferences always produce the same score, and the score can explain itself.

The model does perception. Deterministic code does judgement. That is why the app can tell you why, and why it cannot quietly change its mind between two people asking the same question.

What it proved it can read

On an Argentine menu that marks gluten-free dishes with a crossed-wheat icon rather than text, the model flagged exactly the five marked dishes and correctly did not flag the pasta, the pastry or the empanadas. It read a symbol, not a word.

3 · How a photo becomes a ranked menu

  Scan screen  (app/page.tsx)
      │  a File from <input type="file" accept="image/*" capture="environment">
      ▼
  lib/image.ts          downscale to ≤1024px, JPEG q0.72, bare base64
      │                 12.9MB PNG → 194KB. ~400ms.
      ▼
  POST /api/analyze     { imageBase64, mimeType, prefs }
      │                 size guard, shape validation
      ▼
  lib/llm.ts            ONE gemini-3.1-flash-lite call
      │                 schema generated from lib/schema.ts
      │                 3 keys rotated · 2nd model · OpenAI · all in one 40s budget
      ▼
  zod validation        AnalyzedMenu, or a typed error
      │                 nutrition sanity check → one repair pass
      ▼
  lib/scoring.ts        scoreDish(item, prefs) → score, label, reasons
      │                 pure, deterministic, explainable
      ▼
  lib/store.ts          zustand, sorted by score, persisted to sessionStorage
      │
      ▼
  Smart Menu  →  Dish Details  →  Ask about this dish

Why the image is downscaled in the browser

A phone photo is 3–5MB, and base64 inflates it by a third. Vercel rejects request bodies over 4.5MB before our code runs. Without this step the first real photo on stage returns 413 and the demo dies. It also cuts model latency and token cost by roughly five times.

Why the processing screen never navigates on a timer

An early version advanced its progress stages on a timer and pushed to the menu after ~4 seconds. The real call takes 8–20 seconds, so the user was shown the sample menu instead of their own photo, and an error could never appear because the page had already left. The stages are decorative; only the result drives navigation.

The two contracts, and why they mattered

Three people built this in parallel. That worked because two files were agreed before anyone wrote a screen:

  • lib/schema.ts fixes the shape of the data.
  • components/types.ts fixes the props each screen takes.

Abigail built every component against those props. Brandon built the pages and state against the same props. Neither opened the other's files. When the two halves were finally connected, the contract needed zero changes — they fit on the first try.

The rule: pages own data, routing and state. Components own everything visible. A page should not contain a Tailwind class beyond layout.

5 · How the scoring works

This is the part judges probe hardest, because it is the part that makes a recommendation rather than a translation. It is ordinary code — no model involved — and that is the point.

Hard blocks come first

A dish that breaks the diet, or trips a declared allergy, is capped at “limit” no matter what else it has going for it. A veto, not a penalty. Someone who cannot eat gluten is not helped by a coeliac-unsafe dish scoring 60 out of 100.

But blocked dishes still rank against each other

On a menu where nothing fits the diet, an early version pinned every dish to exactly 35 — twelve identical red cards in arbitrary order, with the dish closest to acceptable buried in the middle. That is worse than useless.

Blocked dishes now spread across the band below “limit” by how badly they break the rule. Keto has a natural gradient in carbohydrate. Binary diets have no honest gradient, so calorie load is used purely as a tiebreak. An allergy is not a spectrum — those sink to the bottom.

Keto, same menuBeforeAfter
Prawn & Brie Salad (16g carbs)35 limit33 — ranked first
Beef Filet (24g)35 limit30
Empanadas (38g)35 limit — ranked above the salad23
Ossobuco Sorrentinos (70g)35 limit7

Reasons are written for humans

reasons[] is what the details screen shows under “Why this score”. They read as things a person would say — “38g carbs – not keto”, “Contains gluten”, “High protein (46g)” — not as field names. Negatives matter as much as positives: a coeliac needs to read “contains gluten”, not the absence of a green tick.

Nutrition sanity

The model estimates macros, so it occasionally produces nonsense — a 5000 kcal salad, a steak with no protein. Those are what a judge notices instantly, and scoring reads the numbers directly, so one absurd value drags a dish to the top or bottom for no reason. Implausible macros (out of range, or not adding up to the stated calories) are rejected and re-asked once.

6 · Why it does not fall over

Every request runs inside one 40-second wall-clock budget. Inside it, this ladder:

TierWhatFires when
13 API keys, rotated from a moving start pointAlways. Rotating the start spreads load instead of draining key 1.
2gemini-3.6-flash, a different modelKeys spent, model retired, or contract broken. Rate limits are per model, so this is a different bucket.
3OpenAI gpt-4oSame, when a funded key exists.
—?demo=1Manual. Returns the sample menu in 0.4s without touching a model.

We deliberately do not fall back on a blown deadline or a malformed request. Neither is fixed by asking someone else, and both would just spend what is left of the budget.

Every failure says something true

SituationStatusWhat the user reads
Photo is not a menu422“That does not look like a menu. Try another photo.”
All keys rate-limited429“We are getting a lot of requests.”
Budget exhausted504“That took too long. Try once more.”
Image too large413“That photo is too large.”
Model broke the contract twice200Sample menu, labelled as sample
The rule: the endpoint never returns a blank 500. And when it degrades to the sample menu, the screen says so. Showing someone else's menu as though it were their photo is worse than showing an error — especially to a judge who just photographed their own.

Three layers against a wrong answer

  1. A strict response schema, so the model cannot return prose.
  2. Runtime validation against the same contract that types the app.
  3. A sanity check and one repair pass before anything reaches the screen.

8 · Running the demo

Before you walk up

  • Phone on venue Wi-Fi and mobile data as backup.
  • Load the URL once to warm it. A cold serverless start adds seconds to a request that already takes ten.
  • Use smartmenu-two-ruddy.vercel.app. Not any other deployment.
  • Printed menu in hand. Screen recording saved locally.

The run — about 90 seconds

  1. Pitch, 15s. “You are in Rome, the menu is in Italian, and you are keto. Google Translate gives you words. It does not tell you what you can actually eat.”
  2. Scan. Take the photo live.
  3. Preferences. Three taps. Say them out loud.
  4. Processing. Let the stages run. Do not talk over them — they are explaining the product for you.
  5. Smart Menu. “Ranked against my diet. Green I can eat, red I should skip.” Point at the top and the bottom.
  6. Dish details. Tap the top dish. “Macros, real ingredients, and — this is the part that matters — why it scored that way.”
  7. Close, 15s. “One photo, one model call, no typing. Works on any phone with a browser.”
If it breaks, say nothing about the error. Add ?demo=1 to the URL and keep talking — it answers in under half a second. If that fails, switch to the recording without pausing. Never debug on stage.

Known limits — be honest if asked

  • Menus longer than 20 dishes are capped at 20, in menu order.
  • Nutrition is estimated, not looked up. We sanity-check it and say so.
  • Category tiles are gradient-and-icon, not photographs. Generated photos are wired but were blocked by a daily quota.
  • State lives in the browser session. Nothing is stored server-side, and there is no account.

9 · Questions we expect

“The nutrition is just guessed.”

It is estimated, and we say so on screen. A restaurant does not publish macros; a database lookup on a fuzzy foreign dish name would be an estimate too, just slower. We reject implausible values and re-ask. For should I order this, a directionally right estimate beats a precise number for the wrong dish.

“What if the model is wrong?”

Three layers: a strict schema so it cannot return prose, runtime validation against the same contract that types the app, and a repair pass. And the scoring — the part that gives advice — is not the model at all.

“Why not use a real nutrition database?”

Because the hard part is not the lookup, it is the match. “Trofie al Pesto Genovese” does not appear in any database. You would be fuzzy-matching a foreign dish name to a generic row and calling the result precise.

“Is this just a wrapper around an API?”

The model call is one file. The rest is the judgement layer: a deterministic scorer that can explain itself, a validation and repair pipeline, a three-tier fallback ladder inside a fixed time budget, and a UI that admits when it is showing sample data. The model is a component, not the product.

“What happens on a menu with nothing you can eat?”

You still get a ranking — ordered by how close each dish is to acceptable, with the reason on every card. That case is specifically handled, because it is the case where a diner most needs help.

“Why a web app rather than native?”

You are holding the demo. No install, no TestFlight, no review. It is React either way; the server side exists only because an API key cannot live in browser JavaScript.

10 · What is next

  • Allergen alerts rather than score penalties — the flags are already in the schema.
  • Real nutrition data for the dishes common enough to have it, with the model as fallback for everything else.
  • Restaurant partnerships — a restaurant uploads its menu once and gets a QR code, so the diner skips the photo entirely. That is also the business model.
One line to leave them with: every other tool translates the menu. SmartMenu reads it, understands what is in the food, and tells you what to order.

Appendix A · The contract

lib/schema.ts, in full. Everything downstream is typed from this file — the model request, the API response, the store, the scorer and every component prop. It was frozen before anyone wrote a screen. 

export const Prefs = z.object({
  diet: z.enum(DIETS).default("none"),
  lowCarb: z.boolean().default(false),
  highProtein: z.boolean().default(false),
  noNuts: z.boolean().default(false),
  targetLang: z.string().default("en"),
});

export const Nutrition = z.object({
  calories: z.number(),
  protein: z.number(),
  carbs: z.number(),
  fat: z.number(),
});

export const Flags = z.object({
  vegan: z.boolean(),
  vegetarian: z.boolean(),
  glutenFree: z.boolean(),
  containsNuts: z.boolean(),
});

export const MenuItem = z.object({
  id: z.string(),
  originalName: z.string(),
  translatedName: z.string(),
  section: z.string(),
  category: z.enum(CATEGORIES),
  ingredients: z.array(z.string()),
  nutrition: Nutrition,
  flags: Flags,
  confidence: z.number().min(0).max(1).default(0.8),
});

export const AnalyzedMenu = z.object({
  isMenu: z.boolean().default(true),
  rejectionReason: z.string().nullable().default(null),
  sourceLang: z.string(),
  items: z.array(MenuItem),
});
Why this matters more than it looks. The JSON schema sent to the model is generated from these definitions at runtime, not written by hand. Change a field here and the model request follows automatically, so the two can never drift apart.

Appendix B · The prompt

The complete instruction sent with every photograph, from buildPrompt() in lib/llm.ts. {targetLang} is substituted from the user's preferences. This single prompt does OCR, structuring, translation, ingredient inference, macro estimation and allergen flagging in one pass. 

You are reading a photograph of a restaurant menu.

Return every dish you can read, in the order it appears on the menu.

For each dish:
- originalName: the dish name exactly as printed, including accents. Do not translate this field.
- translatedName: a natural, appetising name in en. Translate the meaning, not word for word. "Tagliata di Manzo con Rucola" is "Sliced Beef with Rocket", not "Cut of Beef with Arugula".
- section: the menu section this dish sits under, translated into en (for example "Starters", "First courses", "Main courses", "Desserts"). If the menu has no sections, infer the most fitting one.
- category: one of pasta, fish, meat, risotto, dessert, salad, other. Pick the closest.
- ingredients: the main ingredients, in en. Include what the dish obviously contains even if the menu does not spell it out (carbonara contains egg and pork).
- nutrition: your best estimate for one restaurant portion as served. calories in kcal, protein/carbs/fat in grams. A plate of pasta is 600-900 kcal, a green salad is 150-350, a grilled fish main is 350-550. Never return zeros.
- flags: vegan, vegetarian, glutenFree, containsNuts. Be careful and be strict:
  - wheat pasta, bread, breaded or battered dishes and most desserts are NOT glutenFree
  - pesto contains pine nuts, so containsNuts is true; so are most pastries and anything with almonds or walnuts
  - anything with cheese, butter, cream, egg, honey, fish or meat is NOT vegan
  - anything with fish, shellfish or meat is NOT vegetarian
- confidence: 0 to 1, how sure you are about this dish. Lower it when the text is blurry or the dish is unfamiliar.

Also return:
- sourceLang: the language the menu is written in, as a short code such as "it", "fr", "es".
- isMenu: true if this image really is a food or drink menu.
- rejectionReason: null when isMenu is true. When the image is not a menu, set isMenu to false, return an empty items array, and put one short friendly sentence here describing what you actually see, such as "This looks like a photo of a person, not a menu."

Return at most 20 dishes. If the menu lists more than that, return the
first 20 in the order they appear and stop.

Read only what is on the menu. Do not invent dishes that are not there.

Appendix B · Notes on the prompt

Four choices in there are worth being able to defend.

Worked examples beat instructions

“Translate naturally” produces literal translations. One concrete example — “Tagliata di Manzo con Rucola” is “Sliced Beef with Rocket”, not “Cut of Beef with Arugula” — changes the register of every dish name in the response. The same trick carries the allergen rules: naming pesto and pine nuts explicitly is what makes the model catch the nut cases the menu never mentions.

Calorie anchors, because the model has no scale

Without “a plate of pasta is 600–900 kcal, a green salad is 150–350”, the estimates drift wildly between dishes on the same menu. The anchors are what make the numbers comparable enough to rank. They are also backed up in code: macros that fall out of range, or that do not add up to the stated calories, are rejected and re-asked once.

The rejection path rides along

isMenu and rejectionReason are in the same response as the dishes. A photo of a face or a receipt comes back as a friendly sentence in one round trip — no second classifier call, no extra latency on the happy path.

The cap is in the prompt, not just the code

We cap at 20 dishes either way, but asking for 20 rather than trimming 39 afterwards saves the generation time for 19 dishes we would throw away. That single line took a 39-dish Spanish menu from a 504 timeout to 20 dishes in 11 seconds.

What is deliberately absent: nothing asks the model to score, rank or advise. It reports what it sees. Every judgement is made afterwards, in code we can read, test and explain.
